R2-1 LOW - A file the program wrote at the 4.8-degree limit still cannot be
  read back on ZONE_TO_GEODETIC or VERTICAL_ONLY. This is N5, not closed.
  Where:
    michspc/spc/convert.py:954-964. convert_point runs to_geodetic, then
      from_geodetic into the SAME zone; zone_to_geodetic calls it with
      source == target.
    michspc/spc/tm.py:487. The forward's domain check has no allowance.
  The 1e-7 allowance (tm.py:212) lets the inverse recover a longitude up to
  9.1e-10 degrees past the limit. The re-projection into the source zone
  then refuses that same longitude.
  Input: GEODETIC_TO_ZONE 17N "1,41.7,-85.8,200,P" writes
    "1,4627612.7742,100559.4963,200.0000,P".
  Read back:
    ZONE_TO_GEODETIC 17N: refused.
    VERTICAL_ONLY 17N: refused.
    (17N -> 2113 and 17N -> 16N convert.)
  The refusal contradicts itself: "The point is at longitude -85.800000,
  4.800000 degrees from the central meridian of zone 17N ... converts only
  within 4.8 degrees".
  Extent: at exactly 85.8 W (17N), 88.2 W (15N) and 82.2 W (16N), Michigan
  points (county set, 0.01-degree steps) written at 4 decimals refuse on
  read-back:
    17N: 339 of 553
    15N: 111 of 229
    16N: 41 of 50
  The strip is about 7e-10 degrees (~0.05 mm) wide, inside the limit.
  The repository's own NCAT anchor at 44.5000, -82.2000, projected into 16N
  at full precision (the input test_utm_16n_to_17n_lands_on_ncats_17n
  builds), also refuses under ZONE_TO_GEODETIC 16N.
  Pins: the job-path pin,
  test_a_file_written_at_the_limit_reads_back_through_the_job, uses only
  latitude 45.0, which reads back by luck. With the allowance seeded to 0
  it still passes, so it cannot fail for the defect it names. Only the
  projection-level pin (test_a_point_exactly_at_the_limit_reads_back)
  catches the seed.
  Fails closed, so this is LOW.
  Fix: whatever forward follows an inverse in one conversion should accept
  the inverse's allowance, or convert_point with source == target should
  reuse the inverse's own convergence and scale instead of re-projecting.
  Pin with 17N 41.7/-85.8 through ZONE_TO_GEODETIC and VERTICAL_ONLY, and
  with the 16N 44.5/-82.2 anchor at full precision.

R2-2 LOW - N4's new sentence is false in its mirror case. That case is the
  commoner blunder: the GUI opens on positive west (#29), and OPUS/NCAT/GPS
  files are negative west.
  Where: michspc/spc/convert.py:1057-1069 (project_point).
  Input: POSITIVE_WEST job, "1,43.0,-84.5,200,P" -> 16N (and 17N, and the
    SPCS2022 TM zone 261001 at 42.3/-83.7).
  Output: "... The longitude given, 84.500000, is east of Greenwich, and
    every Michigan longitude is west of it: if this file's longitudes are
    positive west, check the longitude sign convention chosen for this job."
  What is wrong:
    - The file gave -84.500000, not 84.500000.
    - The advice is conditional on the file being positive west. This file
      is negative west, so the user is steered away from the actual cause:
      the job reads a negative-west file as positive west.
  project_point sees only the convention-applied longitude, so it cannot
  word this correctly.
  Fails closed, so this is LOW.
  Fix: build the sentence where the convention is known (job layer). Name
  the convention in force and the file's own value, e.g. "this job reads
  longitudes as positive west, so -84.5 in the file is 84.5 E; if the file
  is negative west, choose negative west", and the converse. Pin both
  directions.
