R3-1 LOW - A zone-to-zone file written INTO UTM at the allowance's own edge
  does not read back. R2-1's defect, moved from 4.8 to 4.8 + 1e-7.
  Where:
    michspc/spc/convert.py:975. convert_point always passes recovered=True,
      so a State Plane source point gets the inverse's allowance in the UTM
      forward: up to 4.8 + 1e-7 degrees, about 8 mm beyond the limit, even
      though no transverse Mercator inverse produced it.
    michspc/spc/tm.py:625-630. The inverse that reads the written UTM
      coordinate back has the SAME allowance, 1e-7. The 4-decimal write
      adds up to about 1e-9 degrees, so a point written within about 1e-9
      of 4.8 + 1e-7 recovers just past the allowance and refuses.
  Input: ZONE_TO_ZONE 2112 (ift) -> 17N,
    "1,-63665.6573,19302281.4939,200.0,P". This is 43.1328 N,
    -85.8000000997, Michigan land near the Kent/Ottawa line.
  Output: the program writes "1,4786755.1882,109573.2866,60.9600,P".
  Read back, that row is REFUSED on all four paths:
    ZONE_TO_GEODETIC 17N
    VERTICAL_ONLY 17N
    17N -> 2112, which is the job's own source zone
    17N -> 2113
  The refusal contradicts itself: "give longitude -85.800000, 4.800000
  degrees from the central meridian ... converts only within 4.8 degrees".
  Reproduced on 2113->16N, 2112->16N, 2111->17N, 2111->15N,
  260001->16N-2022, 260001->17N-2022, 261016->15N-2022 and
  261001->17N-2022. 740 of 24,446 accepted conversions failed, but the
  sample was weighted toward the edge.
  The strip is about 1e-9 degrees (~0.08 mm) wide, at 8 mm outside the
  stated limit. A real job will almost never land in it, but it is
  deterministic, and it is the exact property the commit message claims.
  The same position typed as latitude and longitude is refused into 17N.
  So DESIGN #72's "17N refuses west of 85.8 W" holds for geodetic input
  and is 1e-7 degrees wide for State Plane input. That is a nit, not a
  finding.
  Fix (lead's call): give the inverse more room than the recovered forward
  - inverse 2e-7, recovered forward 1e-7 - and have the same-zone
  re-projection in convert_point (source == target) accept whatever the
  inverse accepted.
    One hop: writes reach at most L + A; read-back reaches L + A + ~1e-9,
      which is <= L + 2A; same-zone re-projection is fine; a cross-zone
      hop back to the source is fine.
    Round trips (UTM -> SPCS -> UTM) still take only about 2e-9 per hop
      against a margin of 1e-7.
  Pin with the input above through ZONE_TO_ZONE, then ZONE_TO_GEODETIC,
  VERTICAL_ONLY, and back to the source zone.
