R4-1 LOW - A State Plane coordinate the program writes on a round trip from
  UTM can refuse back into UTM. This is R3-1's knife edge, mirrored: the
  write cap is itself an edge.
  Where: convert.py:977-987 gives a zone-to-zone point into a TM zone the
    write cap (RECOVERED, tm.py:166-167). A UTM coordinate written at the cap,
    taken to State Plane and rounded (3 decimals in ift on SPCS 83), comes
    back up to ~2e-9 degrees beyond the cap. That is over the cap, so it
    refuses.
  Input, all real jobs:
    2112 (ift) -> 17N:  "1,743034.6329,19316538.7936,200.0,P"
      writes            "1,5032588.3803,123974.4405,60.9600,P"
    17N -> 2112 (ift):  writes "1,743034.632,19316538.793,200.000,P"
    2112 (ift) -> 17N on that row: REFUSED, "The point is at longitude
      -85.800000, 4.800000 degrees from the central meridian of zone 17N ...
      converts only within 4.8 degrees". The message contradicts itself at
      six decimals, as the third re-confirmation noted.
  So the program's own output, 0.3 mm from the original input, refuses where
  the original converted.
  Rate: inputs that land within 3e-9 of the cap, SPCS -> TM -> SPCS -> TM:
    2112/17N            330 of 8,304
    2113/16N            323 of 8,282
    2111/15N            323 of 8,311
    260001/17N-2022     277 of 8,296
    261016/15N-2022     277 of 8,311
    261001/17N-2022     309 of 8,268
  The strip is ~0.2 mm wide, lying 8 mm outside the stated 4.8.
  test_a_chain_at_the_limit_never_refuses_and_never_creeps cannot see this:
  its chains start at exactly L (a supplied position), never at L + A.
  The commit message says "every coordinate the program writes reads back and
  multi-zone chains cannot creep". The first half is true for a coordinate's
  own zone and its geodetic; it is not true for the round trip.
  Judgement: this is inherent. Any finite write cap has an outermost write
  whose round trip lands a rounding step past it, and another tier would only
  move the edge (four rounds have now moved it: 4.8 -> 4.8+1e-7 ->
  4.8+1e-7/2e-7). Recommend recording it beside the existing residual rather
  than another tier: a State Plane point within ~2e-9 degree of the write cap
  converts into UTM once; its round-trip output may refuse; it never writes a
  wrong number.

R4-2 LOW - A geodetic file the program writes from a UTM coordinate in the
  write tier refuses back into that UTM zone.
  Where: SUPPLIED is held to exactly L (by design, tm.forward). But
    ZONE_TO_GEODETIC writes the longitude it recovered, up to L + A + ~1e-9,
    at 8 decimals.
  Input: 17N -> geodetic on "1,4786755.1882,109573.2866,60.9600,P" (itself
    written by 2112 -> 17N) writes "1,43.13278379,-85.80000010,60.9600,P"
    and DMS "85-48-00.00036 W".
    GEODETIC_TO_ZONE 17N on that row: REFUSED, with the same self-
      contradicting "-85.800000, 4.800000 ... only within 4.8".
    GEODETIC_TO_ZONE 2112: converts.
  Sweep: 53,496 of 53,496 geodetic positions recovered at the write cap and
  rounded to 8 decimals refuse into their own TM zone. That is everything
  beyond L + 5e-9.
  Judgement: a consequence of the two rules standing together; neither is
  wrong. DESIGN.md #72's "nothing the program writes fails to read back"
  needs this exception named. The third re-confirmation filed it as a nit
  under R3-1 ("1e-7 degrees wide for State Plane input"). It is now a stated
  property, so it is filed here.

R4-3 LOW (false sentence) - Same-zone hops are not capped at the write
  allowance.
  Where: tm.py:110-113 says "It is the cap on every coordinate the program
    writes". tm.py:132-134 says "A chain of conversions cannot creep past the
    read allowance, because every hop that writes into a transverse Mercator
    zone is capped at the write allowance again."
  But a same-zone zone-to-zone job (convert.py:983-984, REREAD) writes at the
  READ tier.
  Input: 261001 m -> 261001 ift -> 261001 m -> ... (a legitimate unit-change
    job, repeated). It starts from a coordinate written at the cap, at
    41.7 N.
    hop 4: the written coordinate lies beyond L + A + overshoot
    hop 226: REFUSED
  The same chain at 45.0 N passes the cap at hop 3 and does not refuse in
  5,000 hops. Single-unit same-zone chains on 17N, 16N and 261001 never pass
  the cap.
  Underlying fact, pre-existing and not from 2b7a2d7: the inverse series is
  0.26 mm off PROJ at 4.8 degrees. So a 17N -> 17N identity job moves the
  northing -0.229 mm per run, -10 mm after 50 runs; 0.1 mm per run at
  4.0 degrees; 0 at 3.0 degrees. It is within the stated 0.5 mm, and
  recorded in DESIGN #72 as "positions within 0.26 mm".
  Judgement: wording. Unreachable in real use, and it fails closed. The two
  sentences should say the write cap holds for a write into a DIFFERENT
  zone; a same-zone re-projection is held to the read allowance.
